## Fit in Pathweft

Keep the five existing Maintenance cards and current table layout. Add a compact
**Recommendation** column to Startup, Services, Windows tweaks and optional
Windows apps. Row details explain the effect, applicability, dependencies and
source. Separate recommendation from current state and from observed resource
usage. A running or automatic service is not inherently unnecessary.

Use four plain-language outcomes:

| Label | Meaning |
| --- | --- |
| Keep enabled | Documented feature/dependency would be lost, or this is required by an enabled Pathweft capability. |
| Optional | Can be considered if the named feature is not used; explain exactly what stops working. |
| Advanced | Material tradeoff or build-specific behavior; no default selection. |
| Not assessed | No matched, reviewed rule. Never infer safety from a familiar name, low usage or a missing catalogue entry. |

Use text plus a small icon/color; color alone is insufficient. Do not add a
percentage safety score or claim that a donor's recommendation is a measured
performance benefit. Read the installed service description, startup mode and
dependencies alongside curated guidance. Distinguish **Manual** from **Disabled**
and **Windows default** from **the user's saved original state**. Third-party
startup entries need exact identity/publisher/product matching; unknown software
stays unassessed. Low recent CPU/RAM does not prove an entry is dispensable.

The smallest useful adoption is a bundled, versioned JSON rule catalogue with
stable IDs, supported Windows builds, exact target, suggested action, reason,
feature loss, source link and verification date. It feeds the existing rows and
selected detail well; it must not execute downloaded scripts or add another daemon.
Configuration/catalogue import must not supply arbitrary privileged commands.
Keep Pathweft's exact-state journal and external-change checks rather than a
donor's hardcoded reset-to-default values. Qualify individual rules in Sandbox,
including a dependent feature and Restore, before marking them assessed.

## Highest-value source findings

- **WinUtil:** `config/tweaks.json` offers categorized descriptions and source
  links. Essential/advanced categories are useful presentation cues, not a safety
  oracle. Its “Services - Set to Manual” entry also contains Disabled changes
  and hardcoded original types: show each actual action and retain our original
  state instead of transplanting the group or its reset values.
- **CrapFixer / Bloatynosy:** `TweakItem.cs` and `Data/WinRules.ini` expose
  descriptions, OS/version applicability, restart requirements, related registry
  values and current-state detection. Bloatynosy also groups mutually exclusive
  alternatives. These are good MIT donors for a small inspectable catalogue and
  scan/results presentation. Their default values must not replace exact Restore.
- **Harden Windows Security:** the Service Manager separates full inventory from
  its short recommendation list. Its configuration/details view includes startup
  type, account, dependencies, triggers, privileges and executable metadata.
  Borrow relevant read-only details, filtering and sorting, without importing
  security enforcement, drivers or protected-service reconfiguration.
- **Sophia Script / SophiApp:** granular functions, conditions and explicit
  consequences. Sophia's DiagTrack notes specifically mention Xbox achievements
  and Feedback Hub effects. SophiApp's requirements/readers demonstrate build and
  architecture checks. Borrow applicable facts/readers with notices; omit their
  unrelated firewall, network and security actions.
- **optimizerDuck:** concrete Safe/Moderate/Risky badges, app caution lists and
  a Startup reader covering Run/RunOnce, folders and packaged MSIX/UWP StartupTask
  entries. The packaged-entry reader is a useful later coverage candidate.
  Its registry flag toggling is not a replacement for Pathweft's source-bound
  Restore. Its GPL code needs an explicit compatible distribution assessment
  before copying into the present MIT source tree.
- **Atlas:** `docs/services-startup-policy.md` is especially useful as a review
  checklist. At this pin it keeps most reviewed services at Windows defaults and
  documents feature loss and deployment scope. For example, OneSyncSvc relates
  to mail/contact/calendar apps, and TrkWks maintains moved-file shortcut/OLE
  links. Server/VDI/IoT advice is not automatically Windows 11 desktop advice.
  Derive rules from the linked Microsoft documentation, not wholesale playbooks.
- **RyTuneX:** separate risk, recommendation reason, technical details, current
  verification, restart and rollback state. Its scan → preview → apply → verify
  → rollback flow fits our existing lifecycle; no universal optimizer score is
  needed. AGPL source is not a drop-in MIT donor.
- **privacy.sexy:** explicit Standard/Strict/unrecommended levels, rationale,
  source documentation and revert scripts. These classify privacy tradeoffs,
  not general performance or disable safety. AGPL code/catalogue reuse needs
  compatible licensing; prefer primary facts and an independently curated rule.
- **Winhance:** build ranges, prerequisites, dependencies, subjective preferences,
  nullable recommendation/default values and advanced unlocks are useful design
  evidence. Its **PolyForm Shield 1.0.0** includes a noncompete restriction. Do not
  copy its implementation into this overlapping maintenance feature without
  suitable permission/licensing. Use the available MIT donors for implementation.

## Verification before any recommendation ships

For each adopted rule: exact supported target/build, original state, intended
effect, dependent-feature behavior, actual apply/readback and exact Restore must
be demonstrated in the appropriate disposable guest. Unknown or inaccessible
facts remain explicit and do not acquire an “Optional” label. Resolve disagreements
against primary Windows/vendor documentation. Keep unrelated network/DNS,
third-party package management, security enforcement, hardware/thermal monitoring,
remote control and image-building features outside the requested modules.

This investigation establishes useful donor patterns and reuse constraints. It
does not establish that every installed service or startup item can already be
classified, or that any proposed tweak improves this machine's performance.
