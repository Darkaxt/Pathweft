## Private recorder (elevated, through the administrator broker)

The test recorder ran with `PATHWEFT_PROFILE` set, so its session names carry the profile's instance suffix. The signed-in recorder kept running both times: its session was still listed, and its heartbeat was fresh.

**Run 1, attempt-3 publish:**
- Command lines came from the kernel session (meta `command_lines` = `kernel`).
- No lost, missed or dropped events.
- Masking: `--token ***`, `https://***@example.com` and `password=***`. No text row contains a probe secret.
- Starting folders: 4 of 69 new processes. Every process that lived under 2 s had none, which led to b0d2f97.

**Run 2, attempt-9 publish (f44dff4), about 70 s:**
- Again: command lines from `kernel`, no lost, missed or dropped events, the same masking, and 0 secret rows.
- Both probe processes have their command line and the starting folder `recorder-cwd`.
- Starting folders, by how long each stored process lived:

  | Lifetime | Stored | With folder |
  | --- | --- | --- |
  | Under 0.5 s | 94 | 79 |
  | 0.5 s to 3 s | 34 | 34 |

  All 15 still without a folder lived under 250 ms. The spec allows this: the folder is null when the process already ended.
- Twenty 0.3 s probes ran in a row. One was stored, with its command line and folder. The other 19 are counted as tiny runs on their workload, as designed: a run is stored only if it lasted 1 s or used 50 ms of CPU, 1 MiB of I/O or 64 MiB of memory (ActivityRecorder.cs:261).
- The recorder used 1.0 s of CPU over 70 s, with 29 MB of private memory.
- 10 stored runs have no command line:
  - 7 ended while the recorder was starting, before rundown.
  - 3 started later and lived under 0.7 s.

  These are not caused by delivery lag, because a late command is still matched when rows are written. The cause is not confirmed. It is pending as [issue #12](https://github.com/Darkaxt/Pathweft/issues/12), with its verification condition.
