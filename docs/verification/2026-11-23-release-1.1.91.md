# Release 1.1.91 verification (S62, CORE-28)

Source: `b4742fb` (tag `v1.1.91`). Spec 1.54, plan S62.

## Scope

- CORE-28: folder sizes on a busy drive. Drive-root containment in SizeCache, changes below a row taken together once a second, changed rows take the index service's total after it has read the change journal, an interrupted walk is not restarted at once, repeated invalidation skips repeated cache deletions.
- CORE-28 addendum (owner: "If we have the indexer service why is it taking so long in generating the analysis?"): Analyze space waits for an index store that is still loading (at most 90 s); the administrator analysis passes the index preference to its elevated worker; the index service applies each journal batch so a file seen before its folder's reused NTFS record keeps its size in the folder totals.

## Diagnosis on the owner's PC (read-only)

- 1.1.90 window: UI thread about 12% of one processor with live analysis open; the process about 100% from PaneView.Measure walks of his C: panes restarting on every change (dotnet-trace).
- Analyze space on C: showed no Indexed row. The live service answered the C: top-level folders in 0.36 s (`pwindex sizes`), and their own last-write times were hours to days old, so the SEARCH-10 settle rule was not the cause. His window runs an elevated administrator session (scheduled task "Pathweft administrator session", started 5 s after the window); in 1.1.90 the elevated worker ran the space walk with the index off. That process used about 90% of one processor during the measurement. Attribution of the elevated process is inferred from start order; its command line is not readable without elevation.
- The 1.1.91 space scenario (attempt 4) read the installed index service reporting fixture folder `branch-059` at 380,016 of 386,016 bytes while listing its `nested\item-000.bin` of 6,000 bytes: the record-reuse ordering loss fixed in the addendum.
