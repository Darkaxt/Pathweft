# Release 1.1.83 verification (2026-11-20)

Release: https://github.com/Darkaxt/Pathweft/releases/tag/v1.1.83 (tag v1.1.83 = 6b62885, main and codex/s8-native-delivery).

**Scope:**
- S19a (spec 1.44): the index service ships and registers in `{app}\services\file_index`. The service side was merged from the index service thread (IS9, 2e46d75 / source 0617d39).
- SPACE-01 (spec 1.42): Analyze space is the command bar button only.
- DELIVERY-05 (spec 1.45): the owner's decision of 2026-11-19, after asking why the installation root held QuickLook DLLs, Performance-MCP.md and so many .NET DLLs: "is better practice to trigger the .Net dependency installation over bundling the libraries in each insalled program".
  - Pathweft is framework-dependent on the Microsoft .NET 10 Desktop Runtime (x64), and Setup installs that runtime when it is missing.
  - An update removes the runtime copy that earlier releases left behind.

The installed 1.1.82 root had 328 entries. About 264 of them were the bundled runtime: System.\*, WPF, coreclr/clr\*, hostfxr and 13 satellite folders. The 1.1.83 package root has 50 files and 13 folders. Size changes:
- portable zip: 665 MB to 591 MB;
- setup: 460 MB to 408 MB.

QuickLook.MediaInfo.dll and QuickLook.ApkReader.dll stay. They are the MediaInfo report and APK parser libraries behind PREVIEW-01/29; the QuickLook application is not involved. Their reference XML doc files are no longer shipped.

## Defects found by validation

1. **The declared gated publish command still said `--self-contained true`** (attempt 5 of ticket 0df0c38c).
   - The source change in scripts/Build-Development.ps1 did not reach the release, because the readiness declaration carries its own `dotnet build -t:Publish` command.
   - The publish still contained hostfxr.dll and coreclr.dll, and its runtimeconfig had includedFrameworks.
   - Recorded with build-fail and corrected in the declaration.
2. **Setup's runtime signature check would have refused Microsoft's valid installer** (fixed in 27e6bac).
   - Windows PowerShell 5.1 inherits PowerShell 7 module paths through PSModulePath, then cannot load Microsoft.PowerShell.Security ("Get-AuthenticodeSignature … module could not be loaded"). This was reproduced on this PC.
   - The check now resets PSModulePath to the machine value.
   - Against the real download (aka.ms/dotnet/10.0/windowsdesktop-runtime-win-x64.exe, 10.0.15, 60,066,584 bytes) it reports Valid, signer `CN=.NET, O=Microsoft Corporation`, exit 0.
3. **The package probe still expected `index\pathweft-indexd.exe`** (fixed in 6b62885).
   - Invoke-S8PackageChecks threw on that check and stopped the remaining probe checks.
   - The probe now requires `services\file_index` and refuses an `index\` folder.
   - It also checks the DELIVERY-05 layout: no hostfxr, coreclr, CoreLib or WPF assembly; a framework reference to Microsoft.WindowsDesktop.App; no satellite folders, root XML docs or root Performance-MCP.md.

Ticket 0df0c38c reached the gate's limit of three corrections of the publish check. It was closed with this evidence and renewed for the same stage as 5744e6c0a8961beb6ecd82247dee4ae2.

**Tooling trap, not a product defect.** In a background shell, `pwsh -File scripts/Reuse-ReleaseSources.ps1` hung for 40 minutes on inherited stdin (0.3 s CPU, no children). With `</dev/null` it finished in 10 s. The package script now closes stdin for every pwsh call.
