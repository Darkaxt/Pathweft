## Release stage

Release stage s49g-release-1.1.74 used ticket 4f265b23bb05f4f497886bec53148709.

- **Attempts 1–3 (26b448f) built.**
  - S4 (the end-to-end archive test) failed on ZIP AES read-back. 7-Zip's ZIP writer refuses a non-ASCII password with E_INVALIDARG, even with AES. This was reproduced against the built DLL; the same password works for 7z and RAR.
  - A measurement also showed that rars' volume size excludes the per-volume headers and the recovery record. At 1 MiB with a 3% recovery record, part1 was 1090502 bytes.
- **Correction 08e9db3** (attempts 4–6, all exit 0):
  - the dialog refuses a ZIP password outside printable ASCII, with the 7-Zip reason;
  - the RAR payload is shrunk for headers and the recovery record, and every part is checked against the size asked for.
- **S4 on 08e9db3** then failed only its own ZIP check. That check required Deflate on every member, but like 7-Zip the ZIP writer stores the incompressible random file ("AES-256 Store", still encrypted).
- **Correction 87b3ed9** changes only that Debug-only check: AES-256 on every member, Deflate on the text member. Attempts 7 (windows-debug), 8 (windows-release-publish) and 9 (packaged-checks) exited 0.
- The publish identifies itself as `1.1.74+87b3ed97e221d381f1171b6e63dafcf997b51f2e`.

**S4 (ARCHIVE-12), each case through the real Archive → Compress… menu and dialog:**
- **7z:** Ultra, LZMA2 with a 1 MB dictionary, solid, password and encrypted names. The file list is hidden without the password. Read back, it decrypts to its inputs as "LZMA2:20 7zAES:19".
- **ZIP:** Maximum Deflate with AES-256. Every file is encrypted and decrypts to its input. The text file is "AES-256 Deflate", and the random file is "AES-256 Store", 7-Zip's own fallback.
- **7z split:** 1 MB volumes named .001…, which join into the verified archive.
- **RAR:** Maximum, solid, 3% recovery record, password, encrypted names and 1 MB volumes. Parts .part1.rar… are 1040786, 1040326, 1040326 and 158066 bytes, all within 1 MB. Names are hidden without the password, and the set decrypts to its inputs.
- **TAR:** stores its inputs.
- **Refusals:** mismatched passwords and a non-ASCII ZIP password keep the dialog open and write nothing.
- **Delete files after compression:** removes the source only after the verified archive is published. The source goes to the Recycle Bin, and Undo brings it back.
- **Remembered settings:** the last settings are remembered, never the password or Delete after.
- **Inside an archive:** Compress… opens the dialog without Delete after and writes the selection beside the archive with the chosen settings.
- **Clipboard:** the original clipboard was restored and verified by an independent STA process after the app exited.

**windows:** the Compress… dialog renders and passes its checks at both scales in the dark, light and original themes.

### Runs that failed on host conditions

- S4's first run on 26b448f refused to touch a clipboard holding a format it can't restore. This is its safety guard; it passed after the owner put text on the clipboard.
- menus-ui failed MENU-08 (menu built with every registered handler within 500 ms) twice on 87b3ed9/08e9db3:
  - run 1, right after the builds: file 548 ms, multiple 569 ms;
  - run 2, right after S4: file 725 ms, folder 555 ms.

  It passed on the same build with the host idle: file 451, folder 233, mixed 203, multiple 228 and background 80 ms. The 26b448f run measured file 322 ms. No menu code changed in these corrections, so the variation is host load. The margin on a file is thin.

## Not verified

- **RAR dictionary and threads** are chosen by the native RAR writer, so no check covers them.
- **ZIP methods other than Deflate** (Deflate64, BZip2, LZMA, PPMd) and ZipCrypto were not each created through the menu. They take the same writer path, and the dialog offers them as 7-Zip does.
