Status: **ACTIVE**. This records prerequisite evidence; no SAB criterion is yet
complete and no production adapter has been selected or installed.

## Observed baseline behavior (3.9.25)

- Native guest Win-key input opens StartAllBack. Real guest key input of
  `powershell` produces the existing Programs and Settings groups.
- Programs contains Windows PowerShell and its x86 shortcut. Invoking the native
  program result launches the expected PowerShell window.
- Settings contains PowerShell developer entries. Invoking the developer entry
  opens Settings at the page containing the PowerShell execution controls.
- These results were observed with WSearch stopped, no SearchIndexer process,
  and existing Start-menu shortcuts present. Programs and Settings therefore do
  not universally require a running WSearch service on this exact combination.
  This is bounded baseline evidence, not preservation proof for a new adapter.
- The guest service's initial configuration was Disabled. A separate attempt to
  start it failed with service-specific status `3489660962`; the guest was
  restored to Disabled. Running-service and indexing-exclusion comparisons
  remain unverified. The host's WSearch remains Running/Automatic.
- Host custom Games and Modding categories are libraries containing multiple
  roots. Their real membership must drive Everything scopes; extension-only
  grouping would change the requested semantics. Personal paths stay private.

## Remaining advancement blockers

### Current-build diagnostic findings

On 3.9.28, actual guest Win-key input and typing again produce the native Programs
and Settings groups with WSearch stopped. The observed forwarding function in
this DLL is RVA `0x3fa58`; it reaches the same qualified Shell32 query interface.
The 3.9.25 forwarding offset is not reused. The updated-build program launch is
recorded below; updated-build Settings launch verification remains pending.

An early observer installed before the first query found additional query-folder
interfaces. Their observed calls included SearchFolder's native view callback;
the recovered `053b4a86` interface is a folder-type GUID getter, not a result
source. The callback also emitted standard `SFVM_BACKGROUNDENUMDONE` (48) for a
normal completed query. Cancellation/generation attribution is still unqualified.

A controlled ingestion experiment used standard COM on the actual menu UI thread.
`IShellFolderView` QueryInterface succeeded. The native folder's
`ParseDisplayName`, with its recovered `ParseOriginalItem` bind-context option,
successfully wrapped a real harmless filesystem fixture into a child PIDL.
However, `IShellFolderView::AddObject` returned `E_NOINTERFACE`; no row appeared.
The returned folder/view references and PIDL were released, and normal groups
remained present. Interface availability therefore does not establish working
insertion. Direct insertion through this legacy method is ruled out for this view.
This was an ABI diagnostic, not a validated feature or an Everything-backed result.

The native-authenticated ingestion bundle has SHA-256
`031b69787b9a3e0d6d0c00e89a025c1c637efc89226cf280dd68f7cbf0a4a32c`.
The add/ref-release result is in
`ev_6a51d622b0fb1aec007fd14fcfa8d5246caa99b3ae11f01592b7ab41301b66ab`;
the callback completion observation is in
`ev_d3e156f9e5934e8dd4ad8cd201bf345cf05ae288e0c1b9a29d541feb0d9c8904`.

Standard COM service lookup from the query view reaches its hosting
`IExplorerBrowser`. An explicit UI-thread read after the native groups rendered
confirmed that `GetCurrentView` returns the same `IShellView` used by query
dispatch. Both legacy `IFolderView` item counts were zero and `Items` returned
element-not-found despite four rendered native results; both rejected
`IResultsFolder`. The stale-view explanation is therefore ruled out for this
observation. This does not establish the underlying grouped-result model.
References were released on the menu UI thread. The authenticated bundle is
`current-browser-contracts-final-01.json`, SHA-256
`c7e7f0865a4aca034ffa1cc55b401bb11053715649b6ecc03f9fb7462e23cfcfb`.

On 3.9.28, invoking the native Windows PowerShell result launched the actual
System32 executable with `CreateProcessW` succeeding; its guest window was then
closed through UI Automation. Invoking See more results reached
`ShellExecuteExW` with `search:query=powershell` from a worker whose stack includes
StartAllBack RVA `0x2b882`. The guest displayed a cannot-find error for that URI;
dismissing it returned false/error 1223. This establishes the observed handoff
boundary, not successful full-results presentation or a selected adapter design.
The passive observer was unloaded, its Frida session detached, and a subsequent
guest window inventory still showed the same Explorer PID and taskbar. Native
evidence is `ev_c2bf44d3bec3071c4ba4d0b3ce6323f6c7457d0b3ce62eda4c5f5cf3e2b77c29`,
authenticated bundle `native-actions-current-01.json`, SHA-256
`63402257584f562ff285b62a36893fe721d8f4a7f58269701c9ba170cba8ab45`.

Additional guest-only indexer diagnostics did not produce a working file-result
baseline. A fresh data-directory attempt lacked a complete directory layout;
it cannot qualify that configuration. A separate original-directory test again
failed with service-specific status 3489660962, with the service finally
Stopped/Disabled and its original data-directory setting restored. The original
root was already uncompressed before startup, so directory compression is not
supported as the cause. Sandbox-specific incompatibility remains a hypothesis,
not an established limitation. No further identical start/configuration retry is
justified without new root-cause evidence.
